**全案共通の運用ルール（各案の「やらせ方」はこれを前提にする）**

- **レーンA「一発」**：ツールなし。1回の応答で成果物（コードやファイルの中身）を出させ、運営がそのまま保存して動かす。人間の手直しは禁止。
- **レーンB「エージェント」**：ファイル作成・コマンド実行・ブラウザでの確認ができる同等の環境で、制限時間内に自走させる。各社純正のエージェントを使うか共通のハーネスを使うかは回ごとに統一して記録する（各環境の機能差は要確認）。
- モデルの設定は各社の既定値のまま。モデル名・実行日・環境・所要時間を成果物と一緒に記録する。

- 再試行は「起動しない」「提出物が欠けている」など比較そのものができない場合に限り、同じプロンプトで1回まで。表示には「再試行あり」と付ける。
- 生成のブレ対策として、各モデル2回ずつ実行し、2回とも掲載して採点は平均を取る（発信で良い方だけ見せる場合はその旨を書く）。
- 採点はモデル名を伏せて A〜E のラベルで行い、対応表は採点が終わってから公開する。

## 案1：【ゲーム】お題「あと5分」1ボタン60秒ゲーム

### 狙い
同じお題・同じ操作制限（1ボタン）・同じ技術制約（HTML 1枚）で作らせ、「お題をどうゲームの仕組みに落とし込むか」という発想力と、「触って気持ちいいか」という手触りの作り込みの差を見る。仕様が小さいので完走しやすく、差はアイデア・演出・難易度調整といったセンスの部分に集まる。お題の解釈がモデルごとにバラけること自体が見どころになる。

### 具体的なタスク内容
- **題材**：お題「あと5分」。二度寝、締め切り、終電、カップ麺など解釈は自由。ただし説明文だけでなく、ルールや仕組みに反映させる。
- **素材**：なし。画像・音声・フォントの持ち込みは禁止。絵は Canvas／CSS／SVG で描き、効果音は Web Audio API で生成する。
- **必須要素**
  - 操作は1ボタンのみ（スペースキー、または画面のクリック／タップ。どちらも同じ動作）。長押し・連打・タイミングの使い分けは可。
  - 1プレイは最大60秒。時間切れかミスで終わり、スコアとリトライ方法を表示する。
  - 時間がたつほど難しくなる。
  - タイトル画面にゲーム名と1行の遊び方を表示する。
  - 16:9を基準に、ウィンドウの大きさに合わせて拡大縮小する。スマホの縦持ちでも崩れない。
  - ハイスコアを localStorage に保存する（使えない環境でもエラーで止まらない）。
  - 自動テスト用のフック `window.GAME = { state, score }`（state は `"title"`・`"playing"`・`"over"` のどれか）。
- **制約**：単一の `index.html`。外部ライブラリ・CDN・外部ファイルは禁止。コンソールエラー0。
- **完成条件**：Chrome の最新版でファイルを開くだけで動き、タイトル→プレイ→終了→リトライが一周できること。

### 成果物の形式
- `index.html`（ゲーム本体）
- `NOTES.md`（お題の解釈、遊び方、こだわった点、既知の不具合を10行以内）
- 運営が作るもの：各作品の60秒プレイ録画（MP4、1280×720）、タイトル画面のスクショ（PNG）
- **5モデルの並べ方**
  1. 5作品＋お題カードの2×3分割動画。同じプレイヤーが各作品を遊んだ録画の冒頭15秒を同時に再生する。
  2. Sunagaku Site Labs に5作品を A〜E のカードで並べ、クリックするとその場で遊べるページを作る。

### やらせ方
初回プロンプト（レーンA・B共通）：

```text
単一の index.html だけで動く「1ボタン60秒ゲーム」を作ってください。お題は「あと5分」です。

【必須仕様】
- 操作は1つだけ：スペースキー、または画面のクリック／タップ（どちらも同じ動作）。長押し・連打・タイミングの使い分けは可。
- 1プレイは最大60秒。時間切れかミスで終わり、スコアとリトライの方法を表示する。
- 時間がたつほど難しくなること。
- お題「あと5分」を、説明文だけでなくルールや仕組みに反映すること。
- タイトル画面に、ゲーム名と1行の遊び方を表示する。
- 16:9を基準に、ウィンドウの大きさに合わせて拡大縮小する。スマホの縦持ちでも崩れないこと。
- 効果音は Web Audio API で生成する（音声ファイルは使わない）。最初の操作までは音を鳴らさない。
- ハイスコアを localStorage に保存する（使えない環境でもエラーで止まらないこと）。
- 画像・音声・フォント・外部ライブラリ・CDN は読み込まない。CSS と JavaScript はすべて index.html に書く。
- 自動テストのため、window.GAME = { state, score } を常に最新に保つ。state は "title"・"playing"・"over" のどれか。
- コンソールエラーを出さないこと。

【提出物】
1. index.html
2. NOTES.md（お題の解釈、遊び方、こだわった点、既知の不具合を10行以内で）

質問はせず、迷った点は自分で決めて NOTES.md に書いてください。
```

- **共通条件**：素材なし。レーンAは1応答（コードブロックで出たものを運営がそのまま保存）。レーンBは制限時間30分で、ブラウザで自分のゲームを動かして確認してよい。
- **一文プロンプトとの相性：◎**。「お題『あと5分』で、1ボタンだけで遊べる60秒のブラウザゲームを index.html 1枚で作って」でも完走できる。ただし `window.GAME` のフックが入らないので自動テストは減る。一文版は「おまけレーン」として別枠で並べると、各モデルが頼まれていない何を足すかも見える。
- **途中質問・追加指示・再試行**：共通ルールどおり。真っ白で起動しない場合のみ1回再実行。難しすぎる・バグがある程度では再実行しない。

### 比較・スコアの付け方
- **足切り（自動、○×で表示）**：起動する／1ボタンに反応する／60秒のランダム入力で例外が出ない／`over` からリトライで `playing` に戻る／コンソールエラー0
- **人間評価（ブラインド、10人以上、各作品を2回ずつプレイ）100点**
  - もう1回遊びたいか（リプレイ欲）：30
  - お題の料理の仕方（意外性と納得感）：20
  - 手触り（入力への反応、演出、音）：20
  - 見た目（統一感、読みやすさ）：15
  - 完成度（バグ、難易度の上がり方、説明なしで遊べるか）：15
- **直感的な見せ方**：「もう1回遊びたい順」の得票数をそのまま順位にする。加えて「解釈マップ」（横軸：反射神経↔頭脳、縦軸：シリアス↔コミカル）に5作品を置き、モデルの発想の癖を1枚で見せる。
- **自動指標（Playwright）**：平均FPS、ファイルサイズ、入力から画面が変わるまでの時間、ランダム入力ボットの平均生存時間（難易度の目安）。人手で「タイトル画面を見て10秒以内に最初の操作ができた人の割合」も測る。

### 実行コストと難易度
- **想定実行時間**：レーンAは数分／モデル、レーンBは最大30分／モデル（5モデル並列なら約30分）
- **必要な環境・ツール**：Chrome、Playwright（自動テストと録画）、動画編集ソフト、静的ホスティング
- **失敗しやすい点**：音の自動再生制限（最初の操作前に鳴らそうとして無音になる）、スマホでクリックとタッチが二重に反応する、高解像度の画面で Canvas がぼやける、難しすぎる／簡単すぎる
- **運営の手間**：テストスクリプトの初回作成に2〜3時間（以後は使い回せる）、プレイ録画と編集に2〜3時間、ブラインド試遊の人集め
- **難易度**：低〜中。5案の中で最も完走しやすい

### 発信での見せ方
- **切り口**：「同じお題『あと5分』で5つのAIにゲームを作らせたら、解釈が全部違った」。1ポスト目で「もう1回遊びたい票」の順位を先に出す。
- **主役の形式：動画＋プレイ可能リンク**。2×3分割のプレイ動画（30秒）を主役にし、リプ欄に5作品の遊べるリンク（Site Labs）を置く。保存用にプロンプト全文の画像を添える。
- **伸ばしどころ**：二度寝ゲームと終電ゲームが並ぶような解釈のズレの意外さと、「自分も遊んでみた」「自分ならこう作る」の引用ポスト。

Xバズり度：★★★★★ — 分割動画・遊べるリンク・解釈のズレの意外さがそろい、見た人が自分で遊んで引用ポストしやすい。

### この案の弱点
- 「面白さ」は主観で、試遊者の好みやゲームの腕前に左右される。
- お題の自由度が高いぶん、ジャンルが違うと単純に比べにくい。逆に全モデルがジャンプゲームに寄ると絵が単調になる。
- 1回ごとのブレが大きく、1サンプルだと運の要素が強い（2回実行が前提）。
- 日本語のお題なので、日本の生活文化への理解が結果に混ざる（見どころでもあるが、純粋な実装力とは別物）。
- 既存の有名ゲームに似た仕組みになった場合の扱い（減点しないが注記する、など）を事前に決めておく必要がある。

## 案2：【3D】設定資料どおりの3Dロボ「ポッコ」を共通スタジオで撮る

### 狙い
同じ設定資料（文字だけ）から3Dキャラクターを作らせ、「文章をどこまで正確に形にできるか（指示解釈）」と「かわいく見せる造形・配色の判断（美的感覚）」の両方を見る。カメラ・照明・台座・背景は運営が用意する共通スタジオで固定するので、違いはモデルの造形判断だけに絞られる。見ながら直せるレーンBでは、自分の描画結果を見て直す粘り強さの差も出る。

### 具体的なタスク内容
- **題材**：夜の図書館を見回る小さなロボット「ポッコ」（このベンチマーク用のオリジナル設定）
- **素材**：運営が用意する `stage.html`（three.js の撮影スタジオ。three.js のバージョンは固定）と、下の設定資料のみ
- **設定資料（チェック12項目）**
  1. 2.5頭身（頭が全高の約4割）
  2. クリーム色で角の丸い大きな頭
  3. 暖かいオレンジに光る丸い目が2つ
  4. 頭のてっぺんにアンテナ1本、先端に電球
  5. ミントグリーン（#7FBFA8 前後）の樽型のボディ
  6. 胸に丸いメーター（針つき）
  7. 首に赤いスカーフ（結び目と垂れた端が見える）
  8. 右手に開いた本
  9. 左手に中が光るランタン
  10. 足のかわりに車輪1つで立つ
  11. 背中に本棚型のリュック、色違いの本が3冊以上
  12. 首を右に少し傾け、好奇心が伝わるポーズ
- **アニメーション**：2秒で一周するループ。ふわふわ上下する／まばたき1回／アンテナの電球が点滅する
- **制約**
  - 提出は `character.js` 1ファイル（ES module、import 禁止）。`build(THREE)` が THREE.Group を返し、`animate(root, t)` が t 秒時点の姿勢を作る。
  - three.js 標準のジオメトリ（Box、Sphere、Cylinder、Capsule、Cone、Torus、Lathe、Tube、Extrude など）と MeshStandardMaterial／MeshPhysicalMaterial だけを使う。外部のモデルや画像は読み込まない（CanvasTexture で自分で描くのは可）。
  - ライト・カメラ・床・背景・ポストエフェクトは追加しない。光る部分は emissive で表現する。
  - 全高 2.0（±0.1）、足元が y=0、正面は +Z 向き。三角形6万以下、メッシュ150個以下。
- **完成条件**：`stage.html` で読み込んだとき、エラーなく表示され、アニメーションがループすること

### 成果物の形式
- `character.js`（主成果物）
- `pokko.glb`：スタジオの書き出しボタン（three.js の GLTFExporter）で運営が書き出す静止ポーズの GLB
- スタジオで自動撮影するもの：8秒のターンテーブル動画（MP4、1080×1080）、正面／横／背面／斜め45°の静止画（PNG）
- **5モデルの並べ方**
  1. 5体を同じ台座に横一列で並べ、同時に回す「ラインナップ動画」（ラベルは A〜E）
  2. 4方向×5体のコンタクトシート画像
  3. 顔のアップだけを5つ並べた画像
  4. Site Labs で5体をマウスで回して見られるページ

### やらせ方
初回プロンプト：

```text

【キャラクター：夜の図書館を見回るロボット「ポッコ」】
1. 2.5頭身（頭が全高の約4割）
2. クリーム色で角の丸い大きな頭
3. 暖かいオレンジに光る丸い目が2つ
4. 頭のてっぺんにアンテナ1本、先端に電球
5. ミントグリーン（#7FBFA8 前後）の樽型のボディ
6. 胸に丸いメーター（針つき）

【アニメーション】

【書き方のルール】
- export function build(THREE) で THREE.Group を返し、export function animate(root, t) で t 秒時点の姿勢を作る。import は書かない。

- ライト・カメラ・床・背景・ポストエフェクトは追加しない。光る部分は emissive で表現する。
- 全高 2.0（±0.1）、足元が y=0、正面は +Z 向き。三角形6万以下、メッシュ150個以下。
```

- **共通条件**：`stage.html` と設定資料のみ。レーンAは1応答。レーンBは制限時間30分で、`stage.html` を実際に開き、スクショを見ながら直してよい。
- **一文プロンプトとの相性：○**。「three.js で、夜の図書館を見回るかわいいロボットを作って」でも成立はするが、スタジオに読み込むための決まり（関数名・向き・大きさ）がないと横並びで撮影できない。一文版は「自由演技」として別枠にし、設定資料版を本番にする。
- **途中質問・追加指示・再試行**：共通ルールどおり。スタジオに読み込めない（関数名の違い・構文エラー）場合のみ1回再実行。向きや大きさの違反は再実行せず減点する。

### 比較・スコアの付け方
- **設定への忠実さ 30**：12項目を「できている1／一部0.5／ない0」で採点（3人が採点して多数決）。○×表にするとそのまま比較画像になる。
- **魅力 25**：ブラインド投票「どの子を連れて帰りたいか」
- **造形の丁寧さ 20**：部品のつながり、浮きやめり込みがないか、細部の作り込み
- **色と質感 10**：配色のまとまり、金属とプラスチックの描き分け
- **アニメーションの生命感 10**：3つの動きがあるか、かわいく動くか
- **技術規定 5**：全高・向き・三角形数・エラー0
- **自動指標**：スタジオが Box3 で全高と向きを測り、三角形数・メッシュ数・FPS・コンソールエラーを自動で記録する。
- **個性の見せ方**：「設定への忠実さ（横軸）×魅力（縦軸）」の散布図。設定に忠実だが地味なモデル、設定を崩してでもかわいくするモデル、といった性格が1枚で分かる。

### 実行コストと難易度
- **想定実行時間**：レーンAは数分／モデル、レーンBは最大30分／モデル。撮影は自動で1体あたり5分ほど。
- **必要な環境・ツール**：Chrome、three.js（CDNでバージョン固定。どの版にするかは実施時点の安定版から選ぶ：要確認）、Playwright（撮影の自動化）、ffmpeg
- **失敗しやすい点**：部品が浮く・めり込む、背中を向けて立つ、左右の手を取り違える、古い three.js の書き方（廃止されたAPI）でエラーになる、大きさの単位を間違える
- **運営の手間**：スタジオ作成に半日（照明・台座・自動撮影・GLB書き出し・ラインナップ表示）。一度作れば、設定資料を差し替えるだけで次回以降も使える。
- **難易度**：中。コードは1ファイルで済むが、空間の把握（部品の位置合わせ）で差が出る。

### 発信での見せ方
- **切り口**：「同じ設定資料から、5つのAIが3Dロボを作った」。1ポスト目に5体が並んで回る動画と、「設定12項目を全部守れたのは○○」という結論を出す。
- **主役の形式：動画**。ラインナップ回転動画（8〜10秒、ループ）を主役にし、2枚目に設定資料の画像、3枚目に忠実さの○×表を付ける。リプ欄に回して見られるリンクを置く。
- **伸ばしどころ**：「どの子がかわいい？」の投票（X の投票機能）と、「ランタンが頭から生えた」ような失敗のおかしさ。

### この案の弱点
- デザインの好みは人によって割れ、評価者の属性（デザイナーか一般の人か）で順位が変わる。
- 画像禁止のため、SVGで絵を描く力が見た目の差を大きく左右し、「LPを作る力」全体の評価としては偏る。
- LP比較はすでに見慣れた題材で、新しさを出しにくい。
- 架空の商品名が実在の商品と重なる可能性がある（要確認）。
- Google Fonts の読み込みや表示環境で見た目がぶれる。

## 自分の推し案

**案2：【3D】設定資料どおりの3Dロボ「ポッコ」を共通スタジオで撮る**
