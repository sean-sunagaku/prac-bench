# ラウンド1提案：Gemini 4 Neon

## 案1：『軌道ポストマン』1画面・重力スリングショット宅配ゲーム制作

### 狙い
物理演算の正確さ、ステージ設計のバランス感覚、演出・効果音・UIを含めた「手触り（ゲームフィール）」の美意識という総合力の差を浮かび上がらせるのが狙いである。学習データに定型実装が溢れているスネークやテトリスを避け、惑星の重力井戸を使う独自ルールの宅配ゲームにすることで、モデルの素の設計力とデバッグの粘り強さを測れる。ドラッグ＆リリースの直感操作に収めることで、専門知識のない人でも30秒遊ぶだけで完成度と個性の違いを体感できる。

### 具体的なタスク内容
- **題材**：宇宙の小型郵便カプセルをスリングショット操作（引っ張って離す）で発射し、惑星の重力を利用して軌道を曲げながら配達ステーションへ着陸（ドッキング）させる2D物理パズルゲーム。
- **素材**：外部画像・音声・外部CDNライブラリは一切禁止。標準ブラウザAPI（HTML5 Canvas 2D または SVG＋Web Audio API）のみで完結させる。
- **必須要素**：
  1. タイトル画面（1クリックで開始）、ステージ選択（1〜3）、即リトライボタン（`R` キーにも対応）。
  2. 仕掛けが段階的に増える **全3ステージ**：
     - **Stage 1**：惑星1つを使った基本スリングショット（重力の曲がりを学ぶ導入）
     - **Stage 2**：双子惑星＋公転する小惑星（障害物を避けるタイミング読み）
     - **Stage 3**：重力井戸＋反射バンパーまたはワープゲート＋任意回収の「星の小包」3個
  3. 引っ張り中に表示される **予測軌道ライン**（実際の物理演算と整合していること）。
  4. 手触り演出：飛行軌跡トレイル、衝突時の失敗演出、ドッキング成功時の演出、Web Audio APIによる手続き生成効果音（発射・星回収・衝突・クリア）とミュート切替ボタン。
  5. HUD：ステージ番号、試行回数、回収した星の数（0〜3）、全3ステージクリア後のリザルト画面。
- **制約**：
  - 単一HTMLファイル（`index.html`）に収め、オフライン環境でローカル起動できること（外部通信ゼロ）。
  - 論理解像度 `960×540`（16:9）基準で画面中央にレスポンシブ表示し、スクロールバーや見切れを出さないこと。
  - 惑星中心付近での重力発散（無限大加速）を防ぎ、全3ステージが実際にクリア可能であること。
- **完成条件**：最新Chromium系ブラウザで `index.html` を開いた際にコンソールエラー0件で起動し、マウスドラッグのみでStage 1〜3を通してクリアできること。

### 成果物の形式
- **出力形式**：単一HTMLファイル（`index.html`）＋運営側が記録するプレイ比較動画（MP4）＋代表画面キャプチャ（PNG）。
- **5モデルを同じ画面・同じ尺度で並べる方法**：
  - 全モデルを論理比率 `16:9`（`960×540`）に統一しているため、X発信では「5画面同時比較動画（2×3グリッド、空き1枠にモデル名・ステージ進行表示）」として同じ縮尺で並べる。
  - Sunagaku Site Labsでは、同一フレームサイズのiframe一覧（またはワンクリック切替タブ）で5本すべてをその場で遊べる実物比較ページとして公開する。

  ```text

  【ルール・必須要素】
  - マウス／タッチのドラッグ＆リリースで発射方向と強さを決め、引っ張り中に実際の物理演算と整合する予測軌道ラインを表示すること。
  - タイトル画面（1クリックで開始）、ステージ選択（1〜3）、即リトライボタン（Rキー対応）、ミュート切替ボタン、クリア後のリザルト画面を備えること。

  - 論理解像度960×540（16:9）基準で見切れやスクロールバーなく収めること。
  - 全3ステージが実際にクリア可能な物理パラメータと配置にすること。
  - 仕様の細部で迷う点があれば質問せず、あなたが最善と考える設計で完成させてください。
  ```
- **共通素材・条件・制限時間・利用可能ツールの考え方**：
  - 共通素材：なし。
  - 制限時間：15分（要確認：各モデル実行ハーネスの最大ターン数およびタイムアウト上限）。

  - 途中質問には応答しない（質問で停止した場合はそのまま未完扱い）。
  - 追加指示は禁止。
  - 白画面や致命的構文エラーで起動不能な場合、本スコアは「起動不可（0点）」と明記した上で、観察用の別枠として1回だけエラーログを渡した「リトライ救済版」を分けて記録する。

### 比較・スコアの付け方
- **直感的な見せ方**：Stage 1の初回ショットからクリアまでと、Stage 3の挑戦シーンを並べた30秒の5分割プレイ動画＋「3分試遊した人間評価者の一言所感」。
- **評価軸ごとの配点案（100点満点）**：
  - プレイ可能性・物理整合性（30点）：3ステージすべてクリア可能か、予測軌道と実軌道が一致するか、異常加速や詰みがないか
  - ステージ設計・面白さ（25点）：3ステージの段階的な変化と「もう1回やりたくなる」難易度設計
  - ビジュアル・UI明瞭さ（25点）：初見で操作が伝わるか、色設計・視認性・世界観の統一感
  - 手触り・演出・音（20点）：軌跡・衝突・成功の爽快感、Web Audio効果音の心地よさ
- **自動測定できる客観指標**：
  - Playwright起動時のコンソールエラー／未処理例外件数（0件が基準）
  - 外部ネットワークリクエスト件数（0件であること）
  - Canvas非空白確認およびドラッグ操作前後の描画差分（操作に応答して動くか）
  - 平均FPSの安定性、HTMLファイルサイズ・コード行数（観察用）
- **モデルの個性が見える評価**：総合点だけでなく、「物理の堅実さ」「アート方向性（ミニマル幾何学／レトロアーケード／絵本調など）」「演出の凝り度」「難易度の優しさ」の4軸レーダーとスタイルタグで性格の違いを見せる。

### 実行コストと難易度
- **想定実行時間**：生成5〜15分／モデル（5モデル計30〜60分）＋運営側の試遊・録画30〜45分。
- **必要な環境・ツール**：Chromium系ブラウザ、Playwright（自動検査用・任意）、画面録画ツール（OBS等）。すべて無料・ローカル完結。
- **失敗しやすい点**：惑星中心に近づいた際の `1/r^2` 発散による画面外ワープ、予測軌道と実物理の刻み幅ズレ、Stage 3の配置ミスによるクリア不能。
- **運営側の手間**：中程度。5本を実際にクリアまで遊ぶ手間はあるが、1本3〜5分で完了し、バグ自体も面白い観察ネタになる。

### 発信での見せ方
- **Xでの主役形式**：**短い比較動画（30秒の5分割同時プレイ動画）＋ プレイ可能リンク**（リプライ欄またはSunagaku Site Labsへの導線で5本すべて遊べる形にする）。
- **Xで伸びる型との相性**：タイムラインで自動再生される「動く成果物」と「5モデル対決の構図」の相性が抜群。冒頭に結論・順位（「1位は〇〇、重力バグでカプセルが宇宙の彼方へ消えたのは〇〇」）を先行提示しつつ、重力発散やクリア不能ステージといった「予想外・失敗の面白さ」を切り出すと引用リポストが伸びやすい。さらに「実際に触れるプレイ可能リンク」と共通プロンプトの公開がブックマーク（保存）を生む。
- **X投稿の切り口**：30秒の5分割同時プレイ動画を冒頭に置き、「同じプロンプトで重力スリングショットゲームを作らせたら、アートも物理も別物になった」と発信。リプライで珍プレー集と5本のプレイ可能リンクを繋ぐ。
- **Sunagaku Site Labs**：5モデルの実物HTMLゲームをブラウザ上でそのまま遊べる比較ページを公開し、読者が手触りを直接比べられるようにする。

**Xバズり度：★★★★☆** — 動く5分割プレイ動画・物理バグの笑い・実際に遊べる実物リンクの3拍子が揃い伸びやすいが、AIミニゲーム比較自体はXの定番枠であり、企画の鮮度面で頭一つ抜ける工夫が要る。

### この案の弱点
- 「ゲームの面白さ」はプレイする人間の好みやゲーム習熟度に左右されるため、主観評価のブレを抑えるには複数人試遊または「予測軌道一致」「3ステージクリア可否」など客観項目を厚くする必要がある。
- エージェント環境でブラウザ自己テストが使えるか否かが完走率に強く影響するため、全モデルで検証ツールの有無を完全に揃える必要がある。
- ゴール判定を極端に大きく作った「簡単すぎるゲーム」がクリア率だけで有利にならないよう、レベルデザインの妥当性を人間が確認する必要がある。

### 同一条件・成果物の明確さ
外部素材や外部ライブラリを一切使わず標準ブラウザAPIのみで完結するため、特定モデルの専用機能に依存せず、全モデルへ完全に同一の条件・制限時間で任せられる。唯一の条件統一ポイントはローカルブラウザでの自己動作確認を許可するか否かだが、全モデルで有無を揃えれば公平な比較が成立する。成果物も論理解像度 `960×540` の単一HTMLファイル（`index.html`）1点に明確に定まり、LPと同様にブレなく横並び比較できる。

## 案2：『雨宿りする郵便配達ロボ』台座付き3Dキャラクター制作（GLB共通スタジオ比較）

### 狙い
3次元空間での座標・構造の把握力、キャラクター造形のセンス（シルエット・愛嬌・背面までの作り込み）、PBRマテリアル表現の差を、照明のごまかしが効かない同一スタジオ環境で暴くのが狙いである。「傘の柄を握る」「濡れた台座に立つ」「小物と情景を作る」というパーツ間の物理的な接触要件を入れることで、空間認識の破綻（パーツの浮遊や貫通）と細部へのこだわりが一目で露呈する。さらにプレビュー画像を自分で見て直す工程を含めれば、モデルの視覚的な自己修正力と粘り強さも観察できる。

### 具体的なタスク内容
- **題材**：「雨のバス停で傘をさして待つ、小さな郵便配達ロボット」のスタイライズド3Dキャラクターと円形ミニジオラマ台座。
- **素材**：外部3Dアセット・外部画像テクスチャは禁止。すべてPythonスクリプト（Blender `bpy`）によるプロシージャル造形とプロシージャルPBRマテリアルで作成する。
- **必須要素**：
  1. **郵便配達ロボット本体**（高さ約1.0〜1.3m目安）：表情が伝わる頭部（バイザーや目・アンテナ）、郵便らしさのある胴体（ロゴ風の意匠やスリット）、左右の腕・脚、手紙が覗く配達バッグ、背面ディテール（バッテリーや蝶番など背面から見ても作り込まれていること）。
  2. **傘の保持**：ロボットの片手が、開いた傘の柄を**浮遊や不自然な貫通なく握っている**こと（傘生地・骨・石突・柄の構造があること）。
  3. **円形ジオラマ台座**（直径2.0m、上面 `z = 0`）：濡れた舗装と水たまりの質感差に加え、小型バス停標識・小型ポスト・ベンチのうち最低2種を配置すること。
  4. **マテリアル設計**：塗装金属、傘生地（布または半透明）、バイザー発光（Emission）、濡れた路面（Roughness差）など最低4種の質感を作り分けること。
- **制約**：
  - 全体が幅2.2m × 奥行2.2m × 高さ2.2m以内に収まり、正面が `-Y`、上方向が `+Z`（Blender標準）であること。
  - 最終成果物を `model.glb` として書き出し、カメラ・ライトは含めない（または運営側の共通スタジオ読み込み時にメッシュ・マテリアルのみ抽出する）こと。
  - 三角ポリゴン数は **5,000〜150,000 triangles** の範囲内に収めること。
  - 実行環境のBlenderバージョンを全モデルで固定すること（例：Blender 4.2 LTS ※要確認：実際のベンチマーク環境に導入するBlenderバージョン）。
- **完成条件**：モデルが作成した `build.py` を共通Blender環境で実行し、`model.glb` がエラーなく出力され、運営側共通スタジオでターンテーブル動画と四面図を書き出せること。

### 成果物の形式
- **出力形式**：3Dモデル本体（`model.glb`）＋生成スクリプト（`build.py`）＋運営側共通スタジオで書き出した360度ターンテーブル動画（MP4）＋四面図＆ワイヤーフレーム一覧画像（PNG）。
- **5モデルを同じ画面・同じ尺度で並べる方法**：
  - 5モデルの `model.glb` を、**完全に同一のBlender共通スタジオ（同じ3点照明・同じ背景色・同じ床グリッド・同じカメラ距離と回転速度）**に読み込み、1本の「5体同時360度ターンテーブル比較動画（MP4）」と、「5列×4段の比較シート（正面・斜め・背面・ワイヤーフレーム）」を作成する。
  - Sunagaku Site Labsでは `<model-viewer>` 等を使い、読者が5体のGLBをマウスで自由に回転・拡大比較できるWeb3D展示室を設ける。

### やらせ方
- **初回に渡すプロンプト文案**：
  ```text
  BlenderのPythonスクリプト（build.py）を書き、「雨のバス停で傘をさして待つ、小さな郵便配達ロボット」の3Dキャラクター＋円形ジオラマ台座を作成して、model.glb として書き出してください。

  【必須要素】
  - 郵便配達ロボット本体（高さ約1.0〜1.3m）：表情のある頭部、郵便らしい胴体、左右の腕と脚、手紙が少し覗く配達バッグ、背面ディテール（バッテリー等）まで360度作り込むこと。
  - 片手で開いた傘の柄を、浮遊や不自然な貫通なく正しく握っていること。
  - 直径2.0m・上面z=0の円形台座に、濡れた路面と水たまり表現、およびバス停標識・小型ポスト・ベンチから2種以上を配置すること。
  - 塗装金属・傘生地・発光パーツ・濡れた路面など、4種類以上のPBRマテリアルを作り分けること。

  【制約・環境】
  - 外部3Dデータ・外部テクスチャ禁止。すべてbpyスクリプトで生成すること。
  - 全体は 2.2m×2.2m×2.2m 以内に収め、正面は -Y、上は +Z とすること。
  - 三角ポリゴン数は5,000〜150,000の範囲内に収め、GLBにはカメラとライトを含めないこと。
  - 実行環境は Blender 4.2 LTS です。同封の preview.py を使って正面・斜め・背面・上面のプレビュー画像を確認し、空間の破綻や見た目を改善してから最終版を仕上げてください。
  - 細部のデザインは質問せず、あなたの美的判断で完成させてください。
  ```
- **共通素材・条件・制限時間・利用可能ツールの考え方**：
  - 共通素材：運営側が全モデルに配布する確認用レンダースクリプト `preview.py`（`model.glb` から4視点PNGを数秒で出力）。※要確認：全5モデルの実行環境で画像閲覧ツールが同じ条件で使えること。もし一部環境で画像入力不可なら、公平性のため全モデルとも `preview.py` なしのコード一発生成条件に統一する。
  - 制限時間：20分（プレビュー確認・修正ループ込み）。
  - 利用可能ツール：Python、Blender CLI（`blender --background --python ...`）、生成画像の閲覧。
- **「一文プロンプトだけ渡す」方式との相性**：**中程度（△〜○）**。一文でも造形センスの差は激しく出るが、向き・大きさ・台座の有無がバラバラになると同一スタジオで同じ尺度に並べにくくなるため、正面方向・サイズ上限・GLB出力名だけは共通条件として渡すのが実用的。
- **途中質問・追加指示・失敗時の再試行の扱い**：
  - 途中質問は不可。制限時間内の自己エラー修正・プレビュー見直しは自由（何回直したかも記録して公開する）。
  - 制限時間内に `model.glb` が出力されなかった場合は未完扱いとし、API名の軽微なバージョン差による失敗のみ「最小修正の参考枠」として本スコアとは別掲する。

### 比較・スコアの付け方
- **直感的な見せ方**：同じ照明・同じ速度で5体が同期回転する15秒ターンテーブル動画（特に背面が回ってきた瞬間の「作り込み vs 手抜き」の差が強烈に伝わる）＋「手と傘の接合部クローズアップ5枚比較」。
- **評価軸ごとの配点案（100点満点）**：
  - 造形美・キャラクター性（30点）：シルエットの魅力、プロポーション、愛嬌やデザインの独自性
  - 空間整合性・接触精度（25点）：手が傘の柄を握れているか、足や小物が台座に接地しているか、浮遊・貫通がないか
  - 360度完成度・ジオラマ情景（20点）：背面の作り込み、バス停や水たまりなど物語性の豊かさ

## 案7：『事故ゼロなのに渋滞する理由』触ってわかる自然渋滞インタラクティブ図解制作（単一HTML）

### 狙い
目に見えにくい科学・社会現象を「触って1分で腹落ちさせる」インタラクティブ解説記事（Explorable Explanation）の設計力を測るのが狙いである。ゲーム（案1）の勝敗設計ともLP（案5）の購買訴求とも異なり、**複数車両の追従物理シミュレーションの正確さ・時空図などのデータ可視化センス・非専門家へのわかりやすい日本語ストーリー構成** という知的な総合力の差が浮き彫りになる。「1台だけ一瞬ブレーキを押すと、事故もないのに渋滞の波が後ろへ伝わる」という誰もが身近に感じる題材により、専門知識のない読者でもモデルの説明力と実装力の違いを直感的に体感できる。

### 具体的なタスク内容
- **題材**：事故も車線減少もない高速道路で、なぜ突然「自然渋滞（衝撃波渋滞）」が発生するのかを、円周道路（リングロード）のリアルタイム・シミュレーションを触りながら理解できる日本語インタラクティブ図解記事。
- **素材**：外部画像・外部CDNライブラリ（D3.js / Chart.js / Tailwind等）・外部Webフォント通信は一切禁止。標準の HTML / CSS / Vanilla JS / Canvas / SVG のみで完結させる。
- **必須要素**：
  1. **冒頭インタラクティブ・リングロード実験**：円周道路上を一定間隔・定速で走る車両群（初期22台）をリアルタイム描画し、速度に応じて車体の色（緑＝快走→黄→赤＝渋滞）が滑らかに変化すること。読者が **「1台だけ一瞬ブレーキ」** ボタン（または任意の車両クリック）を押すと、ブレーキ連鎖によって **進行方向とは逆向きに赤い渋滞波が伝播する現象** を再現できること。
  2. **リアルタイム可視化パネル**：シミュレーションに連動して、**時空図（横軸＝時間、縦軸＝道路周回位置、色で速度を表し渋滞波が斜めに後退する縞模様が見える図）** または **平均速度・渋滞車両数・通過交通量のリアルタイム推移グラフ** を描画し、現在値を数値HUDで示すこと。
  3. **3つの実験スライダー＋ワンクリックプリセット3種**：
     - 調整スライダー：①車両台数（12〜34台）、②ドライバー反応遅れ（0.1〜1.2秒）、③自動協調運転車（ACC：車間を滑らかに保つ車）の混入率（0%〜100%）、加えて再生／一時停止／リセット。
     - ワンクリック実験プリセット3種：**「実験1：ガラガラ道路（ブレーキしても消える）」／「実験2：過密道路（1回のブレーキで自然渋滞が発生）」／「実験3：ACC車20%導入（渋滞波が吸収される）」**。
  4. **腹落ちする日本語解説ストーリー（3〜4セクション）**：数式を羅列するのではなく、「なぜブレーキが後ろへ伝わるのか」「臨界密度とは何か」「たった20%の協調運転で渋滞が減る理由」を短い文章とシミュレーション誘導（「まずブレーキを押してみよう」等）で組み立てること。

  - 単一の静的HTMLファイル（`index.html`）に収め、オフライン環境で外部通信ゼロで動作すること。
  - PC（`1440×900`）とスマホ（`390×844`）の両幅で横スクロールやグラフ見切れを起こさないレスポンシブ設計にすること。

- **完成条件**：最新Chromium系ブラウザで `index.html` を開いた際にコンソールエラー0件・外部リクエスト0件で起動し、「1台だけブレーキ」ボタンと3種のプリセット操作で自然渋滞の発生と解消が視覚的に再現できること。

## 案8：『POCKET-LOFI』1画面グルーヴボックス＆シンセサイザー制作（単一HTML・Web Audio API）

### 狙い
これまでのビジュアル・文章・データ中心のベンチマークでは一切測れなかった **「音作り（DSP信号処理）の設計力・リアルタイム音響スケジューリングの精度・ハードウェア風クリエイティブUIの造形美」** を一挙に可視化・可聴化するのが狙いである。外部音源サンプルを禁止し、Web Audio APIのオシレーター・ノイズ・フィルター・エンベロープだけでKick／Snare／Hi-Hat／Bass・Chordを合成させ、さらに3曲の内蔵プリセットまで組ませることで、「聴き心地のよい音楽的なビートと触りたくなる機材UI」を作るモデルと、「耳障りな電子ビープ音とズレるテンポ」になるモデルの差が、再生ボタンを押した瞬間3秒で露呈する。

### 具体的なタスク内容
- **題材**：ブラウザ上で即座にビートメイクと演奏ができる、ポータブルハードウェア機材風の1画面グルーヴボックス＆ミニシンセサイザー **『POCKET-LOFI』**。
- **素材**：外部音声ファイル（`.wav`/`.mp3`等）・外部ライブラリ（Tone.js等）・外部画像・外部CDNはすべて禁止。標準の HTML / CSS / Vanilla JS / Canvas / Web Audio API のみで完結させる。
- **必須要素**：

  4. **リアルタイム音響ビジュアライザー**：`AnalyserNode` を用いたオシロスコープ波形またはスペクトラム表示を、機材ディスプレイ部にリアルタイム描画すること。

  - 単一の静的HTMLファイル（`index.html`）に収め、オフライン環境で外部通信ゼロで動作すること。

- **完成条件**：最新Chromium系ブラウザで `index.html` を開いてPlayを押した際にコンソールエラー0件・外部リクエスト0件で音声が正常に出力され、3種プリセット切替・ステップ編集・BPM／フィルター操作・ビジュアライザー描画が一通り動作すること。
